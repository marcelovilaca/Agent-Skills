# AI-generated content

A practical guide to designing a product feature that generates current content from live sources and serves persisted results. See the companion [SKILL.md](SKILL.md) for the complete rules and procedure.

## Overview

Use a four-stage pipeline: **source reader → model → store → app**. The model transforms retrieved material; it must not create sources or citations. Generate on the server, persist under a stable key (often the date), and have the app read the stored row. When an upstream step fails, return the previous stored copy with a reason rather than fabricating replacement content.

## Triggers and Inputs

Use this approach for daily or on-demand digests, news summaries, briefings, generated indexes, or other product content users expect to be current. It is not intended for a one-off chat answer or a one-time cited report; use a citation-focused workflow for the latter.

Inputs are the live source items, a prompt contract, an allowed output vocabulary/schema, a storage key, and an OpenAI-compatible chat-completions endpoint. If items have topics, define the allowed values in code as well as in the prompt. Source attribution must be copied from the retrieved item, not generated by the model.

## Prerequisites

- A project source reader and a way to test it against both working and failing sources.
- A model endpoint compatible with the chat-completions request shape, plus the model identifier.
- The project's existing persistence and serving layers. This skill does not prescribe a database, framework, feed library, or schema.
- Endpoint configuration supplied through environment variables in a gitignored environment file; never commit an API key.

No provider SDK or generator CLI is required by the guidance. A plain `fetch` is sufficient for the single endpoint shape described in the reference.

## How to Use

### Quick start

1. Choose the output shape and an idempotent storage key, commonly a date.
2. Implement and test the reader first. A successful HTTP response with zero source items should be handled as a failed/empty-source condition, not as a valid blank digest. Test at least one failing source too.
3. Interleave items from multiple feeds (round-robin) before generation so one high-volume source does not crowd out the others.
4. Write a prompt contract that says what material may be used, what must not be invented, the allowed vocabulary, output shape, and length limits. Include two examples demonstrating the desired specific headline/content.
5. Make one real model request and measure it before connecting the feature. Request JSON when supported, then parse the response defensively.
6. Persist the result without overwriting an existing generated row with demo seed data. Serve the stored result; generation may be triggered server-side when a row is absent, but the client must not call the model directly.

### Request and configuration sketch

Set these project environment variables in a gitignored file (values are supplied by the operator/provider; do not commit secrets):

```dotenv
AI_BASE_URL=<OpenAI-compatible API base URL>
AI_API_KEY=<secret supplied securely>
AI_MODEL=<provider model identifier>
```

The endpoint reference uses `POST ${AI_BASE_URL}/chat/completions` with a bearer token and a JSON body containing `model`, `messages`, and generation options. Example options from that reference are `max_tokens: 700`, `temperature: 0.4`, a 60-second timeout, and `response_format: { "type": "json_object" }` when supported. `enable_thinking: false` is useful for supported reasoning-model providers such as Qwen3; do not assume every provider accepts it. Read the model's `content`, not `reasoning_content`, and extract a balanced JSON object if the response includes prose or code fences. See [references/openai-compatible-endpoints.md](references/openai-compatible-endpoints.md) for the client shape and parsing example.

### End-to-end workflow

- Build the reader and test live success, failure, and zero-item responses.
- Define the prompt and schema as a contract; pass source material and the exact allowed topic list.
- Measure the real request. If it is slow, check input count, whether reasoning is enabled, and the output-token budget before increasing timeouts.
- Store generated results idempotently under the chosen key. Ensure demo seeds do not occupy generated keys and are skipped when a generator is configured.
- Serve the stored row. If generation fails, return the stored copy and a reason.
- Test headline specificity, allowed topic values, feed-derived attribution, and the stored-copy fallback.

## Technical Details

### Files, tools, and outputs

This skill provides implementation guidance, not a standalone application, feed reader, database migration, or generator script. Its linked reference is `references/openai-compatible-endpoints.md`; the project owns its source reader, model client, persistence, app code, and tests.

The generated content is stored by the project's persistence layer (usually keyed by date) and consumed by the app. Attribution fields—such as source name and link—come from the retrieved item. Use simple `fetch` for the endpoint rather than adding an SDK for one call shape. Parse JSON defensively even when JSON output mode is requested.

### Verification

Verify that:

- The reader returns real items from a live source and has a tested failure path; a 200 response with no items is not silently treated as a successful empty day.
- A real model call has been timed with the actual prompt; the generated headline names the subject, not just the publication.
- Every topic is in the code-enforced allowed list and source names/links match the feed items provided to the model.
- Writes are idempotent, demo rows do not block generation, and the app reads the persisted row.
- On reader/model failure, the stored copy is served with a reason rather than invented content.

### Safety and limitations

Keep API keys out of source control, logs, and build output. Never let the model select or invent attribution, links, names, numbers, or sources. Do not present stale/demo content as freshly generated; label fallback status with a reason. Disable reasoning for short tasks only when the provider supports the flag. The reference timeout and generation-option values are examples, not a guarantee of provider limits or performance. This skill does not define a provider, database schema, feed implementation, retry policy, or project-specific test command.
